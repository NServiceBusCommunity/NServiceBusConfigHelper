This solution is an NServiceBus endpoint; the facts below describe how it is set up.

## Project facts

 * Solution: `SampleEndpoint.slnx`. The endpoint is `src/SampleEndpoint`, and its name on the transport is `SampleEndpoint`. Renaming it renames its queue.
 * Target framework `net10.0`, SDK pinned by `global.json` (10.0.402). NServiceBus 1.0.0.
 * Packages use Central Package Management: add or change versions in `Directory.Packages.props`, and reference packages without a version.
 * The whole endpoint configuration is in `src/SampleEndpoint/Program.cs`. It is registered with `builder.Services.AddNServiceBusEndpoint(endpointConfiguration)` and starts and stops with the host.
 * Transport: SQL Server.
 * Persistence: SQL Server.
 * Serializer: System.Text.Json. Message classes need a parameterless constructor and settable properties.
 * Connection strings (`SqlServer`) are read from configuration in `Program.cs`; the development values are in `appsettings.json`.
 * `docker compose up -d` starts what the endpoint needs locally.
 * `EnableInstallers()` is on: the endpoint creates its queues and tables when it starts.
 * Tests are in `src/SampleEndpoint.Tests`, with xUnit v3 and NServiceBus.Testing. Run them from the solution directory with `dotnet test`.

## Working with NServiceBus

 * A message is a plain class with no NServiceBus interface. A class in the namespace `SampleEndpoint.Messages.Commands` is a command and one in `SampleEndpoint.Messages.Events` is an event; putting a message anywhere else means NServiceBus does not recognise it.
 * A command asks one endpoint to do something, is named in the imperative, and is sent. An event says something has happened, is named in the past tense, and is published. Never publish a command or send an event.
 * Changing or removing a property of a message breaks messages already in flight and endpoints not yet redeployed. Add properties; do not rename them.
 * A handler implements `IHandleMessages<T>` and is found by assembly scanning: adding the class is enough.
 * Inside a handler, send and publish through the `IMessageHandlerContext` it is given, never through `IMessageSession`: only then are the outgoing messages part of handling the incoming one.
 * Do not catch an exception in a handler to keep going. Let it throw: NServiceBus retries the message, then moves it to the `error` queue.
 * The outbox is on, so a redelivered message is not processed twice as long as the handler's data goes through the persistence's own session. Anything else a handler touches, such as an http call, can still happen twice.
 * Outside a handler, send through `IMessageSession`, as `OrderSubmitter` does.
 * Test a handler by calling `Handle` with a `TestableMessageHandlerContext`, then asserting on its `SentMessages` and `PublishedMessages`. Test code that uses `IMessageSession` with a `TestableMessageSession`. No test needs a transport.

## Features of this endpoint

### Message conventions

 * Commands and events are recognised by namespace, so message classes need no NServiceBus interface or reference.
 * Documentation: https://docs.particular.net/nservicebus/messaging/conventions
 * Configured by `var conventions = endpointConfiguration.Conventions();`.
 * Message classes are plain classes: what makes one a command or an event is its namespace. Every endpoint that exchanges these messages needs the same conventions.

### Sagas

 * A long-running process with its own state: a sample saga that is started by an event and completes on a timeout.
 * Documentation: https://docs.particular.net/nservicebus/sagas/
 * Files: `Sagas/OrderSaga.cs`, `Sagas/OrderSagaData.cs`, `Sagas/CancellationWindowElapsed.cs`.
 * A saga's state is stored by the persistence. Messages for one saga instance are handled one at a time: a concurrent update fails and is retried.
 * A timeout is a message sent to the saga itself with a delay, so it survives a restart.

### Handler ordering

 * When several handlers take the same message, each says which handlers it runs after, and the order is worked out at startup.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.HandlerOrdering
 * Configured by `endpointConfiguration.ApplyInterfaceHandlerOrdering();`.
 * Files: `Handlers/NotifyWarehouseHandler.cs`.

### Retry policy

 * Sets how many times a failing message is retried, immediately and then with a delay, before it goes to the error queue.
 * Documentation: https://docs.particular.net/nservicebus/recoverability/
 * Configured by `var recoverability = endpointConfiguration.Recoverability();`.
 * An immediate retry runs the handler again straight away. A delayed retry puts the message back with a delay that grows by the time increase each round. When both are used up the message goes to the error queue.

### Outbox

 * Stores a handler's outgoing messages with its data in one transaction, so a redelivered message is neither processed nor sent twice.
 * Documentation: https://docs.particular.net/nservicebus/outbox/
 * Configured by `endpointConfiguration.EnableOutbox();`.
 * With the outbox on, the transport has to receive in `ReceiveOnly` mode, which `Program.cs` sets on the transport: consistency between the data and the outgoing messages comes from the outbox record, not from a transaction spanning the queue and the database.

### Auditing

 * Copies every successfully processed message to an audit queue, which ServiceControl reads to show message flows.
 * Documentation: https://docs.particular.net/nservicebus/operations/auditing
 * Configured by `endpointConfiguration.AuditProcessedMessagesTo("audit");`.
 * Something has to read the `audit` queue, normally ServiceControl. Left alone it grows without bound.

### Audit filter

 * Chooses which message types go to the audit queue, with an attribute on the message or a default for the rest.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.AuditFilter
 * Configured by `endpointConfiguration.FilterAuditQueue(FilterResult.IncludeInAudit);`.
 * Messages with no audit attribute: Audit them.
 * Mark a message class with `[IncludeInAudit]` or `[ExcludeFromAudit]` to decide for that type, whatever the default is.

### Heartbeats

 * Tells ServiceControl at a regular interval that the endpoint is alive, so ServicePulse can show when it stops.
 * Documentation: https://docs.particular.net/monitoring/heartbeats/
 * Configured by `endpointConfiguration.SendHeartbeatTo("Particular.ServiceControl");`.

### Custom checks

 * Reports the result of health checks written for this endpoint to ServiceControl: a sample check of free disk space.
 * Documentation: https://docs.particular.net/monitoring/custom-checks/
 * Configured by `endpointConfiguration.ReportCustomChecksTo("Particular.ServiceControl");`.
 * Files: `CustomChecks/DiskSpaceCheck.cs`.

### Performance metrics

 * Sends processing time, queue length and throughput to a ServiceControl monitoring instance, for ServicePulse's monitoring view.
 * Documentation: https://docs.particular.net/monitoring/metrics/
 * Configured by `var serviceControlMetrics = endpointConfiguration.EnableMetrics();`.

### Saga audit

 * Sends every saga state change to ServiceControl, so the history of a saga can be followed.
 * Documentation: https://docs.particular.net/nservicebus/sagas/saga-audit
 * Configured by `endpointConfiguration.AuditSagaStateChanges("Particular.ServiceControl");`.
 * Saga audit sends a message for every state change, which costs throughput. It is meant for development and for diagnosing a problem, not for every production endpoint.

### OpenTelemetry

 * Exports NServiceBus traces and metrics over OTLP, so a message can be followed across endpoints in any OpenTelemetry backend.
 * Documentation: https://docs.particular.net/nservicebus/operations/opentelemetry
 * NServiceBus emits traces and metrics without being asked; this registers its sources with the OpenTelemetry SDK and exports them.
 * Traces and metrics go to `http://localhost:4317` unless the `OTEL_EXPORTER_OTLP_ENDPOINT` environment variable names another collector.

### Serilog

 * Logs through Serilog, with NServiceBus exception details as structured properties, and a log event for each message handled and sent.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.Serilog
 * Configured by `var serilogTracing = endpointConfiguration.EnableSerilogTracing(Log.Logger);`.
 * Message tracing writes an event for every message received and sent, enriched with the message id, type, correlation id and conversation id. Inside a handler, `context.Logger()` is a logger that already carries them.

### FluentValidation

 * Validates messages with FluentValidation as they are received and sent: a sample validator for the sample command.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.Validation#nservicebusfluentvalidation
 * Configured by `endpointConfiguration.UseFluentValidation();`.
 * Files: `Validation/PlaceOrderValidator.cs`.
 * A message that fails validation on the way in is not retried: it goes straight to the error queue. One that fails on the way out throws where it is sent. Pass `incoming: false` or `outgoing: false` to `UseFluentValidation` to check one direction only.

### DataAnnotations

 * Validates messages with the attributes in System.ComponentModel.DataAnnotations as they are received and sent.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.Validation#nservicebusdataannotations
 * Configured by `endpointConfiguration.UseDataAnnotationsValidation();`.
 * Put the attributes on the message's properties, for example `[Required]`. A message that fails validation on the way in is not retried: it goes straight to the error queue.

### SQL attachments

 * The claim check pattern on SQL Server: large content travels beside the message in a table, and is streamed when a handler asks for it.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.Attachments/blob/main/docs/sql.md
 * Configured by `endpointConfiguration.EnableAttachments`.
 * Files: `Messages/Commands/StoreDocument.cs`, `Handlers/StoreDocumentHandler.cs`, `Attachments/DocumentSender.cs`.
 * Attachments are kept in a `MessageAttachments` table, which installers create. `TimeToKeep.Default` keeps an attachment for ten days, or for twice the message's time to be received when it has one.

## What the setup implies

 * **Heartbeats, Custom checks, Performance metrics, Saga audit**: Heartbeats, Custom checks, Performance metrics and Saga audit send to ServiceControl's queues. Until [ServiceControl](https://docs.particular.net/servicecontrol/) has been installed and has created them, those messages have nowhere to go.
 * **Handler ordering, Audit filter, Serilog, FluentValidation, DataAnnotations, SQL attachments**: Handler ordering, Audit filter, Serilog, FluentValidation, DataAnnotations and SQL attachments are NServiceBus Community extensions: MIT licensed, and developers who use them are expected to [become patrons](https://github.com/NServiceBusCommunity/Home#community-backed).
