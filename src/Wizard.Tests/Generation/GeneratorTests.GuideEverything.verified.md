# SampleEndpoint

An NServiceBus endpoint generated by the [NServiceBus wizard](https://nservicebuscommunity.github.io/NServiceBusConfigHelper/new?step=output&host=Worker&transport=SqlServer&persistence=SqlServer&serializer=SystemJson&tests=XunitV3&features=Conventions,Sagas,HandlerOrdering,Recoverability,Outbox,Auditing,AuditFilter,Heartbeats,CustomChecks,Metrics,SagaAudit,OpenTelemetry,Serilog,FluentValidation,DataAnnotations,AttachmentsSql). ## What is in the solution

 * `src/SampleEndpoint`: the endpoint `SampleEndpoint`, hosted as a worker service.
 * `src/SampleEndpoint.Tests`: xUnit v3 tests.
 * `docker-compose.yml`: SQL Server, for running locally.
 * `CLAUDE.md` and `.github/copilot-instructions.md`: the same facts as this guide, written for an AI coding assistant.
 * Transport: [SQL Server](https://docs.particular.net/transports/sql/).
 * Persistence: [SQL Server](https://docs.particular.net/persistence/sql/).
 * Serializer: [System.Text.Json](https://docs.particular.net/nservicebus/serialization/system-json).
 * Features: Message conventions, Sagas, Handler ordering, Retry policy, Outbox, Auditing, Audit filter, Heartbeats, Custom checks, Performance metrics, Saga audit, OpenTelemetry, Serilog, FluentValidation, DataAnnotations, SQL attachments.

Package versions: the newest stable releases as of 2026-10-01; nuget.org was not checked when this was generated.

## Before the first run

1. Install the .NET SDK 10.0.403 or a later feature band; `global.json` pins it.
2. Start the containers the endpoint needs: `docker compose up -d`. Their passwords are in `docker-compose.yml` and `appsettings.json` in the clear, which is fine for a container on a developer's machine and nowhere else.
3. SQL Server starts with no database. Create it once the container is up: `docker compose exec sqlserver /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P NServiceBus-Dev-1 -C -Q "CREATE DATABASE [SampleEndpoint]"`.
4. NServiceBus is licensed by Particular Software. See [licensing](https://docs.particular.net/nservicebus/licensing/) for the options and for where the licence file goes.

## Run it

```sh
dotnet run --project src/SampleEndpoint
```

On startup `SampleOrders` submits one order. The log shows `PlaceOrder` being handled, and the `OrderPlaced` event it publishes being handled in turn.

## How the endpoint is configured

All of it is in `src/SampleEndpoint/Program.cs`, in the order below.

### Transport: SQL Server

Queues are tables in a SQL Server database. No broker to run, and it can share a transaction with the data. [Documentation](https://docs.particular.net/transports/sql/).

```cs
var transport = new SqlServerTransport(sqlServerConnectionString);
```

 * Reads the `SqlServer` connection string. A SQL Server database the endpoint can create tables in.

### Persistence: SQL Server

SQL persistence on SQL Server, with plain ADO.NET and scripts generated at build time. [Documentation](https://docs.particular.net/persistence/sql/).

```cs
var persistence = endpointConfiguration.UsePersistence<SqlPersistence>();
persistence.SqlDialect<SqlDialect.MsSqlServer>();
persistence.ConnectionBuilder(() => new SqlConnection(sqlServerConnectionString));
```

 * Reads the `SqlServer` connection string. A SQL Server database the endpoint can create tables in.
 * SQL persistence generates its table scripts at build time, into `bin/<Configuration>/<TargetFramework>/NServiceBus.Persistence.Sql`. Installers run them on startup; without installers, run them as a deployment step.

### Serializer: System.Text.Json

Json with the serializer built into .NET. No extra package; the usual choice. [Documentation](https://docs.particular.net/nservicebus/serialization/system-json).

```cs
endpointConfiguration.UseSerialization<SystemJsonSerializer>();
```

### Error queue

A message that still fails after its retries is moved to the `error` queue, with the exception in its headers, so the endpoint can carry on with the next one.

```cs
// Where a message goes once every retry has failed. ServiceControl reads this queue.
endpointConfiguration.SendFailedMessagesTo("error");
```

### Installers

The endpoint creates its queues, topics and tables when it starts. That is convenient in development. In production, run [installers](https://docs.particular.net/nservicebus/operations/installers) as a deployment step instead, with rights the running endpoint does not need.

```cs
// Creates the queues, topics and tables the endpoint needs when it starts. Convenient in development.
// In production, run installers as a deployment step, with rights the running endpoint does not need.
endpointConfiguration.EnableInstallers();
```

### Message conventions

Commands and events are recognised by namespace, so message classes need no NServiceBus interface or reference. [Documentation](https://docs.particular.net/nservicebus/messaging/conventions).

```cs
var conventions = endpointConfiguration.Conventions();
conventions.DefiningCommandsAs(type => type.Namespace == "SampleEndpoint.Messages.Commands");
conventions.DefiningEventsAs(type => type.Namespace == "SampleEndpoint.Messages.Events");
```

 * Message classes are plain classes: what makes one a command or an event is its namespace. Every endpoint that exchanges these messages needs the same conventions.

### Sagas

A long-running process with its own state: a sample saga that is started by an event and completes on a timeout. [Documentation](https://docs.particular.net/nservicebus/sagas/).

Files: `Sagas/OrderSaga.cs`, `Sagas/OrderSagaData.cs`, `Sagas/CancellationWindowElapsed.cs`.

 * A saga's state is stored by the persistence. Messages for one saga instance are handled one at a time: a concurrent update fails and is retried.
 * A timeout is a message sent to the saga itself with a delay, so it survives a restart.

### Handler ordering

When several handlers take the same message, each says which handlers it runs after, and the order is worked out at startup. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.HandlerOrdering).

```cs
endpointConfiguration.ApplyInterfaceHandlerOrdering();
```

Files: `Handlers/NotifyWarehouseHandler.cs`.

### Retry policy

Sets how many times a failing message is retried, immediately and then with a delay, before it goes to the error queue. [Documentation](https://docs.particular.net/nservicebus/recoverability/).

```cs
var recoverability = endpointConfiguration.Recoverability();
recoverability.Immediate(immediate => immediate.NumberOfRetries(3));
recoverability.Delayed(delayed =>
{
    delayed.NumberOfRetries(2);
    delayed.TimeIncrease(TimeSpan.FromSeconds(15));
});
```

 * An immediate retry runs the handler again straight away. A delayed retry puts the message back with a delay that grows by the time increase each round. When both are used up the message goes to the error queue.

### Outbox

Stores a handler's outgoing messages with its data in one transaction, so a redelivered message is neither processed nor sent twice. [Documentation](https://docs.particular.net/nservicebus/outbox/).

```cs
// The outbox takes over from the transport's transaction, which then only covers the receive.
transport.TransportTransactionMode = TransportTransactionMode.ReceiveOnly;
endpointConfiguration.EnableOutbox();
```

 * With the outbox on, the transport has to receive in `ReceiveOnly` mode, which `Program.cs` sets on the transport: consistency between the data and the outgoing messages comes from the outbox record, not from a transaction spanning the queue and the database.

### Auditing

Copies every successfully processed message to an audit queue, which ServiceControl reads to show message flows. [Documentation](https://docs.particular.net/nservicebus/operations/auditing).

```cs
endpointConfiguration.AuditProcessedMessagesTo("audit");
```

 * Something has to read the `audit` queue, normally ServiceControl. Left alone it grows without bound.

### Audit filter

Chooses which message types go to the audit queue, with an attribute on the message or a default for the rest. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.AuditFilter).

```cs
endpointConfiguration.FilterAuditQueue(FilterResult.IncludeInAudit);
```

 * Messages with no audit attribute: Audit them. Everything is audited except the types marked [ExcludeFromAudit].
 * Mark a message class with `[IncludeInAudit]` or `[ExcludeFromAudit]` to decide for that type, whatever the default is.

### Heartbeats

Tells ServiceControl at a regular interval that the endpoint is alive, so ServicePulse can show when it stops. [Documentation](https://docs.particular.net/monitoring/heartbeats/).

```cs
endpointConfiguration.SendHeartbeatTo("Particular.ServiceControl");
```

### Custom checks

Reports the result of health checks written for this endpoint to ServiceControl: a sample check of free disk space. [Documentation](https://docs.particular.net/monitoring/custom-checks/).

```cs
endpointConfiguration.ReportCustomChecksTo("Particular.ServiceControl");
```

Files: `CustomChecks/DiskSpaceCheck.cs`.

### Performance metrics

Sends processing time, queue length and throughput to a ServiceControl monitoring instance, for ServicePulse's monitoring view. [Documentation](https://docs.particular.net/monitoring/metrics/).

```cs
var serviceControlMetrics = endpointConfiguration.EnableMetrics();
serviceControlMetrics.SendMetricDataToServiceControl("Particular.Monitoring", TimeSpan.FromSeconds(10));
```

### Saga audit

Sends every saga state change to ServiceControl, so the history of a saga can be followed. [Documentation](https://docs.particular.net/nservicebus/sagas/saga-audit).

```cs
endpointConfiguration.AuditSagaStateChanges("Particular.ServiceControl");
```

 * Saga audit sends a message for every state change, which costs throughput. It is meant for development and for diagnosing a problem, not for every production endpoint.

### OpenTelemetry

Exports NServiceBus traces and metrics over OTLP, so a message can be followed across endpoints in any OpenTelemetry backend. [Documentation](https://docs.particular.net/nservicebus/operations/opentelemetry).

```cs
builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService("SampleEndpoint"))
    .WithTracing(tracing => tracing
        .AddSource("NServiceBus.Core")
        .AddOtlpExporter())
    .WithMetrics(metering => metering
        .AddMeter("NServiceBus.Core.Pipeline.Incoming")
        .AddOtlpExporter());
```

 * NServiceBus emits traces and metrics without being asked; this registers its sources with the OpenTelemetry SDK and exports them.
 * Traces and metrics go to `http://localhost:4317` unless the `OTEL_EXPORTER_OTLP_ENDPOINT` environment variable names another collector.

### Serilog

Logs through Serilog, with NServiceBus exception details as structured properties, and a log event for each message handled and sent. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.Serilog).

```cs
var loggerConfiguration = new LoggerConfiguration();
loggerConfiguration.Enrich.WithNsbExceptionDetails();
loggerConfiguration.WriteTo.Console();
Log.Logger = loggerConfiguration.CreateLogger();

// Serilog takes the place of the host's own providers, so each event is written once.
builder.Logging.ClearProviders();
builder.Logging.AddSerilog();

var serilogTracing = endpointConfiguration.EnableSerilogTracing(Log.Logger);
serilogTracing.EnableMessageTracing();
```

 * Message tracing writes an event for every message received and sent, enriched with the message id, type, correlation id and conversation id. Inside a handler, `context.Logger()` is a logger that already carries them.

### FluentValidation

Validates messages with FluentValidation as they are received and sent: a sample validator for the sample command. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.Validation#nservicebusfluentvalidation).

```cs
builder.Services.AddValidatorsFromAssemblyContaining<PlaceOrderValidator>();

endpointConfiguration.UseFluentValidation();
```

Files: `Validation/PlaceOrderValidator.cs`.

 * A message that fails validation on the way in is not retried: it goes straight to the error queue. One that fails on the way out throws where it is sent. Pass `incoming: false` or `outgoing: false` to `UseFluentValidation` to check one direction only.

### DataAnnotations

Validates messages with the attributes in System.ComponentModel.DataAnnotations as they are received and sent. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.Validation#nservicebusdataannotations).

```cs
endpointConfiguration.UseDataAnnotationsValidation();
```

 * Put the attributes on the message's properties, for example `[Required]`. A message that fails validation on the way in is not retried: it goes straight to the error queue.

### SQL attachments

The claim check pattern on SQL Server: large content travels beside the message in a table, and is streamed when a handler asks for it. An NServiceBus Community extension. [Documentation](https://github.com/NServiceBusCommunity/NServiceBus.Community.Attachments/blob/main/docs/sql.md).

```cs
endpointConfiguration.EnableAttachments(
    () => new SqlConnection(sqlServerConnectionString),
    TimeToKeep.Default);
```

Files: `Messages/Commands/StoreDocument.cs`, `Handlers/StoreDocumentHandler.cs`, `Attachments/DocumentSender.cs`.

 * Reads the `SqlServer` connection string. A SQL Server database the endpoint can create tables in.
 * Attachments are kept in a `MessageAttachments` table, which installers create. `TimeToKeep.Default` keeps an attachment for ten days, or for twice the message's time to be received when it has one.

## The sample messages

 * `Messages/Commands/PlaceOrder.cs` is a command: a request for one endpoint to do something.
 * `Messages/Events/OrderPlaced.cs` is an event: something that has happened, which any number of endpoints can subscribe to.
 * `Handlers/PlaceOrderHandler.cs` handles the command and publishes the event. `Handlers/OrderPlacedHandler.cs` handles the event, which is also what subscribes the endpoint to it.
 * `OrderSubmitter.cs` sends the command from outside a handler, through `IMessageSession`. Inside a handler, always send and publish through the context the handler is given, so the outgoing messages belong to the message being handled.
 * `SampleOrders.cs` submits one order on startup. Delete it, and its registration in `Program.cs`, once the endpoint has real work.
 * The message classes implement no NServiceBus interface: the conventions in `Program.cs` recognise them by namespace.

## Worth knowing

 * **Heartbeats, Custom checks, Performance metrics, Saga audit**: Heartbeats, Custom checks, Performance metrics and Saga audit send to ServiceControl's queues. Until [ServiceControl](https://docs.particular.net/servicecontrol/) has been installed and has created them, those messages have nowhere to go.
 * **Handler ordering, Audit filter, Serilog, FluentValidation, DataAnnotations, SQL attachments**: Handler ordering, Audit filter, Serilog, FluentValidation, DataAnnotations and SQL attachments are NServiceBus Community extensions: MIT licensed, and developers who use them are expected to [become patrons](https://github.com/NServiceBusCommunity/Home#community-backed).
