# SampleEndpoint: instructions for AI coding assistants

Generated by the [NServiceBus wizard](https://nservicebuscommunity.github.io/NServiceBusConfigHelper/new?step=output&host=Worker&transport=RabbitMQ&persistence=PostgreSql&serializer=SystemJson&tests=XunitV3&features=Sagas,Outbox,Serilog). This solution is an NServiceBus endpoint; the facts below describe how it is set up.

## Project facts

 * Solution: `SampleEndpoint.slnx`. The endpoint is `src/SampleEndpoint`, and its name on the transport is `SampleEndpoint`. Renaming it renames its queue.
 * Target framework `net10.0`, SDK pinned by `global.json` (10.0.402). NServiceBus 1.1.0.
 * Packages use Central Package Management: add or change versions in `Directory.Packages.props`, and reference packages without a version.
 * The whole endpoint configuration is in `src/SampleEndpoint/Program.cs`. It is registered with `builder.Services.AddNServiceBusEndpoint(endpointConfiguration)` and starts and stops with the host.
 * Transport: RabbitMQ.
 * Persistence: PostgreSQL.
 * Serializer: System.Text.Json. Message classes need a parameterless constructor and settable properties.
 * Connection strings (`RabbitMQ`, `PostgreSql`) are read from configuration in `Program.cs`; the development values are in `appsettings.json`.
 * `docker compose up -d` starts what the endpoint needs locally.
 * `EnableInstallers()` is on: the endpoint creates its queues and tables when it starts.
 * Tests are in `src/SampleEndpoint.Tests`, with xUnit v3 and NServiceBus.Testing. Run them from the solution directory with `dotnet test`.

## Working with NServiceBus

 * A command implements `ICommand` and an event implements `IEvent`; both live in `SampleEndpoint.Messages`.
 * A command asks one endpoint to do something, is named in the imperative, and is sent. An event says something has happened, is named in the past tense, and is published. Never publish a command or send an event.
 * Changing or removing a property of a message breaks messages already in flight and endpoints not yet redeployed. Add properties; do not rename them.
 * A handler implements `IHandleMessages<T>` and is found by assembly scanning: adding the class is enough.
 * Inside a handler, send and publish through the `IMessageHandlerContext` it is given, never through `IMessageSession`: only then are the outgoing messages part of handling the incoming one.
 * Do not catch an exception in a handler to keep going. Let it throw: NServiceBus retries the message, then moves it to the `error` queue.
 * The outbox is on, so a redelivered message is not processed twice as long as the handler's data goes through the persistence's own session. Anything else a handler touches, such as an http call, can still happen twice.
 * Outside a handler, send through `IMessageSession`, as `OrderSubmitter` does.
 * Test a handler by calling `Handle` with a `TestableMessageHandlerContext`, then asserting on its `SentMessages` and `PublishedMessages`. Test code that uses `IMessageSession` with a `TestableMessageSession`. No test needs a transport.

## Features of this endpoint

### Sagas

 * A long-running process with its own state: a sample saga that is started by an event and completes on a timeout.
 * Documentation: https://docs.particular.net/nservicebus/sagas/
 * Files: `Sagas/OrderSaga.cs`, `Sagas/OrderSagaData.cs`, `Sagas/CancellationWindowElapsed.cs`.
 * A saga's state is stored by the persistence. Messages for one saga instance are handled one at a time: a concurrent update fails and is retried.
 * A timeout is a message sent to the saga itself with a delay, so it survives a restart.

### Outbox

 * Stores a handler's outgoing messages with its data in one transaction, so a redelivered message is neither processed nor sent twice.
 * Documentation: https://docs.particular.net/nservicebus/outbox/
 * Configured by `endpointConfiguration.EnableOutbox();`.
 * With the outbox on, the transport has to receive in `ReceiveOnly` mode, which `Program.cs` sets on the transport: consistency between the data and the outgoing messages comes from the outbox record, not from a transaction spanning the queue and the database.

### Serilog

 * Logs through Serilog, with NServiceBus exception details as structured properties, and a log event for each message handled and sent.
 * Documentation: https://github.com/NServiceBusCommunity/NServiceBus.Community.Serilog
 * Configured by `var serilogTracing = endpointConfiguration.EnableSerilogTracing(Log.Logger);`.
 * Message tracing writes an event for every message received and sent, enriched with the message id, type, correlation id and conversation id. Inside a handler, `context.Logger()` is a logger that already carries them.
